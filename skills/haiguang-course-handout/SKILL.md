# 海光课程讲义（Haiguang Course Handout）

用于把课程大纲、实训清单、厂商培训材料、视频截图、口述稿等，做成一份可交付的学员讲义（Markdown 源 + DOCX，可选 PDF）。
适用于中文技术课程，也适用于其他需要"先对齐、再成稿"的讲义任务。

## 四条硬规矩

这四条优先于下面所有流程细节。

1. **先对齐，再动笔。** 读完所有资料后，先用一轮 3～5 个问题把结构、粒度、理实比例、图表策略、交付格式问清；答案改变结构就再来一轮，直到不再改变为止。详见 [alignment.md](references/alignment.md)。不要凭猜测开工，也不要在没对齐时先写正文再改。
2. **资料覆盖、图表并存。** 资料目录里的每一份资料都要有交代：要么读了，要么在 `outline.md` 里写明"为什么与本讲无关"。不许默默跳过——"穷尽"指**覆盖判断**，不是逐字读完：一个 60 MB 的视频、一份 32 MB 的大纲不必逐字啃，但取舍要写下来。讲义里的原始图（厂商 PPT 截图、产品图、架构图）与重排后的表格**同时保留**。这类讲义往往还要转成视频与 PPT，删掉原图等于丢素材。详见下文"Core workflow"第 3 步。
3. **绝不覆盖用户的 Word 修改。** 用户改过的 DOCX 是事实源，不能用 Markdown 重新生成后覆盖。先备份、再比对、再就地改。详见 [revision-protocol.md](references/revision-protocol.md)。
4. **骨架固定。** 每一讲都按同一副骨架写，缺块就是不合格：

   ```text
   N.1、学习目标
   N.2、<理论节名>（可拆多节，术语表收尾）
   N.3、具体实训内容
   N.4、需要的硬件设施
   N.5、配套视频
   N.6、小结与自测
   N.7、附录（可选）
   ```

   理论归理论、实训归实训：理论节里不许挂"逐步"小节，实训节里不再展开原理。各块的写法见 [lesson-structure.md](references/lesson-structure.md)。

## Core workflow

1. **核对讲次** — 先在课程大纲里定位本讲那一行：讲次、题目、知识点、实训。若大纲与已交付讲义对不上（例如已交付的"第42讲"内容其实是大纲第 43 讲），**停下来问用户**：补做缺的那一讲、按大纲改号、还是顺着编号往下走。不要自行顺延，也不要改完号不吭声。把"讲次 → 大纲行 → 本讲题目"写进 `outline.md`。
2. **对齐** — 读资料，然后按 [alignment.md](references/alignment.md) 提问：章节骨架、内容粒度（哪些照搬原表、哪些重写）、知识部分与实训部分的比例、图表策略（原图 / 重排表 / 两者都要）、交付格式与文件名。把确认过的骨架复述一遍，再开工。
3. **取材** — 逐份过一遍大纲、清单、培训材料、PDF、截图、转写稿，每份给出"读了 / 没读及理由"。规则：
   - 截图与原文优先于转写稿；语音转写常把型号、数值写错（如把 BW1100 写成 BW-1100、把 FP8 写成 LP8），**型号与数字一律以截图/原文为准**。
   - 厂商材料里的参数表，既保留原图，也重排成讲义表格；重排表便于阅读，原图便于后续做 PPT。
   - 图片题注只写画面内容与编号对应关系，**不写来源括注**（不写"（海光培训材料原图）""（H3C 用户指南图2-12）"这类）。出处统一进文末「来源」节或表注。
   - 可核对的事实与教学解释分开写；不编造规格、引用或结论。
4. **起草** — 只维护一份 Markdown 源：普通标题、段落、列表、表格、相对路径图片、必要的 `<!-- pagebreak -->`；YAML frontmatter 只放文档元数据。
5. **排版** — 动笔前读 [lesson-structure.md](references/lesson-structure.md)（教学结构）与 [style-contract.md](references/style-contract.md)（版式）。
6. **构建与校验** — 见"Portable conversion helper"与"Quality gate"；`validate_handout.py` 会检查骨架是否齐全、理论节有没有混入"逐步"、实训任务有没有四列表、单元格里有没有竖线；再渲染页图逐页检查空白页与表题孤儿，然后交付。
7. **交付** — 交付格式按对齐结果（本课程惯例：只交 DOCX，Markdown 作为工作源留在工作目录，不进交付目录）。
8. **修订** — 用户返回改过的 DOCX 时：`revision.py lock` 查占用 → `backup` → `diff` 列清单 → 与用户确认 → 就地改（只碰目标段落）→ 校验 → 再备份。禁止整份重建覆盖。

## 讲义结构约定（本课程）

### 固定骨架

| 节 | 放什么 | 怎么写 |
| --- | --- | --- |
| `N.1、学习目标` | 知识目标、实操目标两组 | 知识目标可说"了解/认识/读懂"，但每条带可判定的达成标志；实操目标用"完成/拆装/识别/判定"这类可观察动词 |
| `N.2、<理论节名>` | 全部知识内容，`N.2.1、` 起 | 可拆成若干小节；术语表是本节最后一小节。节名写成"到货验收与上架接线"这类话题名，不写"理论知识" |
| `N.3、具体实训内容` | 全部动手任务，`N.3.1、` 起 | 一个任务一个 H3 + 一张四列表：`步 / 动作与要领 / 常见错误 / 检查点`；表后一条"红线：…"；任务开头一句写清交付物与验收 |
| `N.4、需要的硬件设施` | 防静电与安全用品、上架与拆装工具、耗材与标识、机柜与供电配套 | 三列表：`名称 / 型号 / 规格 / 用途`；只写本讲真正用到的件，数量按"一套教学工位" |
| `N.5、配套视频` | 视频清单 + 观看节奏 | 三列表：`视频名 / 时长 / 内容要点`；没有实拍素材就明说"待拍"，不拿别的课顶替 |
| `N.6、小结与自测` | 目标回看表、课后自测、参考答案与解析 | 回看表逐条同词对应目标，可加"对应实训"列；写完解析就收尾，不写「下一讲…」这类跨讲衔接 |
| `N.7、附录`（可选） | 课堂填写单、资产台账、检查表 | 41 讲没有、42 讲有；按需要增删，不影响骨架 |

### 编号与标注

- 讲名用 `第41讲 …`；小节用 `41.1、`、`41.1.1、`；表格题注 `表41-1、…`，编号随文档顺序连续。
- 术语表放在理论节（`N.2`）的末尾，不夹在中间，也不放到回顾或附录之后。
- 目标回看表逐条对应学习目标，措辞同义同词。
- 来源节可选。出处**只进文末「来源」节**（没有来源节时进表注），**不进正文句子，也不进图注与表题**。图注与表题里一律不留括号来源，例如不要写「（H3C iFIST 配置指导图3-19）」；`validate_handout.py` 会对这种括注告警。
- 不使用 `[1]` 这类数字引注；来源用平铺条目。
- 不写跨讲衔接（「下一讲…」「为第 N 讲做铺垫」）：讲义自成一讲，讲次顺序属于大纲与开场口径，不放正文结尾。`validate_handout.py` 会对「下一讲」告警。

### 理论与实训的界线

- 理论节只回答"为什么这样规定、看什么、怎么判定"；实训节只回答"手怎么动、做完看哪几项"。
- 禁止把"逐步：…"这类动作小节挂在理论节末尾充当实训；也禁止在实训节里重新展开原理。
- 禁止"为实训打基础""讲清楚这些后面才有落点""为后面拆卡做准备"这类写法。

## Portable conversion helper

```text
python scripts/build_handout.py lesson.md --out-dir output/lesson --formats md,docx
```

`md` 与 `docx` 总是由构建器生成；`pdf` 由该 DOCX 经 Office 转换器导出（LibreOffice Kit，其次 `soffice`/`libreoffice`），保证 DOCX 与 PDF 同一套分页与字体。找不到转换器时退回 ReportLab 渲染并告警。

排版固定、不按文档改：黑体标题 + 宋体正文、正文 11.5 pt、标题 24 / 20 / 18 / 13 pt、精确行距、页眉"课程 / 章"、页脚"标题 · 页码"。frontmatter 的 `heading_font` / `body_font` 只换字体族，不改字号与间距。具体数值见 [style-contract.md](references/style-contract.md)。

## 修订协议（摘要）

```text
python scripts/revision.py lock   <file.docx>        # 是否被 Word 占用
python scripts/revision.py backup <file.docx>        # 时间戳副本
python scripts/revision.py diff   <baseline.docx> <edited.docx>
```

`diff` 输出"删除 / 新增 / 改写 / 格式改动 / 表格改动"五类，每类给段落首行作为定位符。
完整规则（含"Word 占用时怎么办""万不得已必须重建怎么办"）见 [revision-protocol.md](references/revision-protocol.md)。

## Quality gate

- 骨架齐全：`N.1`～`N.6` 六块都在、顺序对、编号连续；理论节里没有任何以"逐步/实训/实操"开头的小节。`validate_handout.py` 会直接拦这一条。
- 讲次有出处：`outline.md` 里写着"本讲 = 大纲第几讲 / 题目"，且与大纲一致；对不上时已经问过用户。
- 学习目标：知识目标有可判定的达成标志，实操目标可观察；目标与回看表一致。
- 实训节：一个任务一张四列表，列头是"步 / 动作与要领 / 常见错误 / 检查点"，表后一条红线；验收写在任务开头。缺表或缺列头会被校验器拦下。
- 硬件节与视频节不是凑数：写的是本讲真会用到的件与真需要拍的片子。
- 正文不解释文档自身：不出现"本节内容出自…""本讲不讲/不做/不在本讲范围内""本讲只做…这一层""为避免误解""需要说明的是"这类句子。想表达范围就写成正面条件，写不成就整句删掉。`validate_handout.py` 会拦。
- 不出现"为实训打底/才有落点/做准备"这类定性。
- 资料穷尽：给出的每份资料都读过；原始图与重排表并存；外来源图在「来源」节有交代，图注保持一行、不挂来源括注。
- 术语在首次出现处解释；单位、精度、口径跟着数字走。
- 表格同口径比较，不隐藏缺失条件；每张表有 `表N-x、…` 题注行；图片 alt 即题注。
- 表格单元格里没有未转义的竖线 `|`（会把这一行拆错列）；正文里没有 ASCII 双引号（会渲染成镜像的 ”）。这两条校验器都管：前者报错，后者告警。
- 标题单独读起来是一条通顺的大纲。
- 本地链接与图片路径可解析；生成的 DOCX 无截断、无缺字、无空页、无表题孤儿（表题与表格必须同页）。
- 不使用 `[1]`、`[^1]` 之类数字引注。
- 修订过的稿子：用户的改动逐条保留，交付前用 `revision.py diff` 复核一次。
