# 修订协议（Revision protocol）

讲义交付后，用户会在 Word 里直接改：换动词、删段落、调字号、加批注。**那些改动是事实源，不能被一次重建冲掉。**

## 铁律

1. 用户改过的 DOCX **不再由 Markdown 重新生成覆盖**。重建会让用户的所有手改消失，且不可恢复。
2. 每次动用户文件之前先备份；每次改完再备份一次。
3. 只改目标段落，其余段落与格式原样保留。

## 三步

```text
python scripts/revision.py lock   <file.docx>        # 先确认没被 Word 占用
python scripts/revision.py backup <file.docx>        # 时间戳副本
python scripts/revision.py diff   <baseline.docx> <edited.docx>
```

`diff` 的五类输出：

| 类别 | 含义 |
| --- | --- |
| `[删除]` | 基线有、用户删掉的段落 |
| `[新增]` | 用户加的段落 |
| `[改写]` | 同一位置文字变了，前后都列出 |
| `[格式]` | 文字没变，字号/加粗/颜色/行距变了 |
| `表 N` | 某张表的行数或单元格内容变了 |

先把这个清单给用户看，确认"这些是你改的、这些是我要改的"，再动手。

## 就地改的原则

- 用 python-docx 直接操作 DOCX：定位段落 → 只改它的 run 文本；需要新段落时**克隆同类段落**（标题克隆标题、正文克隆正文、图注克隆图注），再替换文字，格式自然一致。
- 插入图片时克隆现有图片段落，换 `r:embed` 与 extent，保留居中对齐、段前距、与题注的 keep-with-next。
- 改完必须：`validate_handout.py` + 渲染页图 + `diff` 复核（应当只剩你这次的改动）。
- 页码、表号、图号联动的地方（表题、图注里的"见表41-7"）要一起改，`diff` 会帮你抓漏。

## Word 占用时

`lock` 返回 `LOCKED` 说明文件还开着。**停下来等用户关闭**，不要强写、不要另存成"副本 (2)"制造版本混乱。写不进去时把改动暂存到工作目录，告诉用户"关掉 Word 后我写回"。

## 万不得已必须重建

例如整讲结构大改、或 Markdown 源才是唯一可信版本：

1. 先 `diff` 导出用户改动清单；
2. 重建后逐条重放，并把"重放了哪几条"交给用户核对；
3. 保存前后两份文件，不要删旧的。

### 结构大改：从当前 DOCX 反向抽取 Markdown

要动骨架（例如把混排的四章改回"目标 / 理论 / 实训 / 硬件 / 视频 / 回顾"），又只剩 DOCX 这一个可信版本时，正确做法是**以用户当前文件为源头反向抽取**，不是凭记忆重打：

1. `lock` 查占用、`backup` 备份、把当前 DOCX 导出成纯文本基线。
2. 按文档顺序抽取成 Markdown：`Title→#`、`Heading 2→##`、`Heading 3→###`、`Caption→题注`、项目符号→列表、表格→管道表；图片按顺序导出到 `raw/`，用紧随其后的 Caption 做题注。抽取**只读不写**原文件。
3. 抽取后做段落级比对：原稿多少段、抽取稿多少段，逐条对得上才继续；差一段就停下找原因。
4. 以抽取出的 Markdown 为工作源重排，正文照抄，只动标题、小节归属、表号与交叉引用。
5. 重建后再比一次：把"被改写、被合并"的段落列成清单交给用户，说明为什么改。

42 讲就是按这条走完的：223 段原稿 → 223 段抽取稿逐条对上 → 重排 → 新旧比对列出 114 段差异，逐条说明是改名、换号还是折进表格。

## Markdown 与 DOCX 分叉

一旦用户手改了 DOCX，Markdown 源就过期了：

- 默认以 DOCX 为准继续改；
- 若确实要回到 Markdown（例如后续要批量生成），先用 `diff` 把用户改动逐条补进 Markdown，再以 Markdown 为准；
- 任何情况下都不要"重建一遍看看效果"。
